# ADR017: Bounded replay and checkpoint retention

Accepted implementation refinement,2026-10-12, within T28. PostgreSQL remains authoritative for saved history, usage and workflow ownership. Retention is an internal operator action scoped to one workspace through the ordinary nonowner application role and transaction-local RLS. No public deletion/checkpoint endpoint or maintenance authorization is added.

Checkpoint deletion uses the vendor's public `adelete_thread` API under the same advisory invocation gate as answer and brief workers. Eligibility requires an expired terminal mapping, terminal run and tool execution, no unfinished run jobs, and no reserved usage. Recovery must resolve unfinished work before retention; age alone cannot erase recovery state. A successful delete records `workflow_threads.checkpoint_purged_at`. Both runners check that receipt after acquiring the invocation gate and before opening the saver, preventing a stale pre-gate snapshot from recreating the deleted checkpoint. A failed delete or failed receipt commit is retried idempotently.

The invocation gate and saver use separate database connections. Losing the gate cannot retract a write already issued on the saver connection. Consequently, the mapping and deletion receipt remain and are eligible for another deletion sweep after one hour. This is reconciliation, not a distributed atomic deletion guarantee. Physical application purge must preserve thread identities in the independent deletion manifest before removing mappings. That part, its scheduler and the restore replay drill remain unfinished.

`checkpoint-prune` processes at most100 thread IDs with UUID keyset pagination and a10-second deadline per thread. Busy gates are skipped and revisited on the next sweep starting without a cursor. An empty page or completed cursor does not mean that skipped/ineligible threads have been deleted. Fleet scheduling is T30; the command alone does not establish a wall-clock retention SLA.

`replay-prune` transactionally removes at most100 expired workspace idempotency rows and100 events from terminal runs outside the24-hour replay window. It clears at most100 provider-response bodies older than24hours only when accounting is settled/estimated, the run is terminal or already detached, and no pending run job/reserved attempt needs recovery. It preserves usage totals/tokens/state, saved messages, runs and final history. `FOR UPDATE SKIP LOCKED` avoids competing with live writes and serializes key deletion against reuse. Each invocation has a10-second deadline; a failure rolls back its entire batch. Full batches may need another invocation; busy rows always require subsequent scheduled sweeps. Event expiry continues to use the existing run-created-at API boundary.

These commands implement only the documented ephemeral-data retention slice. They do not acknowledge physical conversation/source/object deletion, remove90-day accounting/audit records, implement identity retention, or certify backup erasure. Source/conversation tombstones and authorization checks continue to apply immediately while complete purge and disaster recovery are developed.
