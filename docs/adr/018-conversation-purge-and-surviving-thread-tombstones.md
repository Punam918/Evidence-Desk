# ADR018: Conversation purge and surviving thread tombstones

Accepted implementation refinement,2026-10-12, within T28. This implements the existing tombstone-first conversation deletion contract. It does not add a public endpoint or change source ownership. Shared knowledge-base documents, source objects and vector points are not conversation-owned and must survive conversation deletion.

`conversation-purge-worker` claims only existing `purge` jobs whose payload identifies a conversation, through a fixed SECURITY DEFINER function returning lease metadata. The function shares purge-claim serialization, is owned by the restricted dispatcher owner, revokes PUBLIC execution and grants only `ed_dispatch`. Source/KB/workspace purge jobs remain available for their respective handlers. Ordinary page work uses `ed_app` with transaction-local workspace RLS and rechecks the current job token, exact payload, matching conversation tombstone, soft-deletion state and creator. Cleanup continues if the original requesting member subsequently leaves; the already-authorized tombstone, rather than a new membership grant, authorizes erasure.

Each claim runs a bounded page with a20-second deadline and lease heartbeat. Transactions acquire admission then workspace locks before changing jobs, usage or slots. No transaction spans saver I/O. Replay caches are removed in100-row pages, including cached conversation titles and associated run/tool responses. One run is processed at a time. All its active jobs receive a new fencing token and cancellation before outstanding usage is settled conservatively. Issued/ambiguous requests are charged at their reserved estimate; not-issued/definite failures release the reservation. Provider response bodies and request hashes are cleared once the worker is fenced. No new model request is made.

Before saver deletion, up to25 workflow IDs are recorded as `entity_type='workflow_thread'` rows in the existing `deletion_tombstones` table. These records contain IDs only and deliberately have no parent FK. They survive physical run/mapping/workspace removal. Public saver deletion occurs under the normal invocation gate; held gates defer progress. Every mapped thread must have a successful tombstone receipt before application cascade can remove its mapping. `checkpoint-prune` now also reconciles these standalone records after1hour, including when the original run and mapping no longer exist. This handles already-issued delayed saver writes after gate loss. It does not claim atomic cross-connection deletion.

After all checkpoint receipts exist, child tool executions, events and jobs are drained in100-row pages before the run is removed. Usage run/conversation references are nulled while content-free token/cost accounting survives. Message pairs and their feedback are removed. Remaining orphan messages/detached accounting are handled in100-row pages. The final conversation deletion, parent tombstone receipt and purge-job completion commit together. Healthy page progress and busy gates do not consume the three infrastructure retries; infrastructure failure leaves the lease for the existing reaper. Repeated failures become dead jobs requiring investigation.

Batch caps constrain deletion work; per-run fencing/settlement and workspace cache discovery are still subject to the existing3-second SQL/1-second lock limits and need T29 load measurements. Thread deletion records remain under the stated35-day deletion-log policy; automatic pruning and independent off-host deletion-log retention/replay are not implemented here. A database tombstone is not itself an independent backup. Full source/object/workspace purge, source-derived answer redaction and the measured restore drill remain T28 work.
