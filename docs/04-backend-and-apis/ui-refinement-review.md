## Chosen visual direction

Use a restrained organization document workspace: stable navigation, readable evidence, compact source metadata and clearly staged work. Retain the blue identity and light surfaces. Make the experience distinctive through the organization of answers and evidence rather than decorative cards, gradients or invented activity.

| Decision | Implementation target |
|---|---|
| Typography |Keep the local/system sans-serif stack; no remote font request. Body/forms16px, answer prose16–17px with1.65–1.75 line height, navigation14px, secondary copy13–14px, metadata at least12px. Current10–11px controls and helper text are too small for sustained use. Headings28–32px, compact page titles24px. |
| Color |Keep ink `#17243a`, blue `#2258bf`, surface `#f7f9fc`, white content. Replace selected-state muted text with a verified token such as `#526174` (approximately5.68:1 on `#edf3ff`). Add shared success/warning/error tokens, each with text labels and verified contrast. |
| Layout |One workspace shell across all workspace routes:240–256px navigation,64–72px topbar,24–32px content gutters. Answer measure approximately68–76 characters; forms/list pages may use the wider content area. At≤1023px use the existing accessible navigation drawer pattern; narrow gutters16px. |
| Controls |44px interaction targets,8px control radius,10–12px panel radius, consistent icons and spacing. One primary action per region. Move destructive controls into an explicit secondary menu/dialog. Keep native semantic controls unless a custom interaction has an accessibility reason. |
| State |Use a small shared vocabulary: ready, processing, needs attention, unavailable, draft, saved. Map backend codes to plain language without changing their meaning. Do not use generic success styling to imply answer truth. |

Split the accumulated global stylesheet into tokens/base, shared layout/components and feature styles. Keep selectors scoped and remove unrelated green/border values currently embedded in comparison/brief rules. A new design-system package or component-library migration is unnecessary.

## Navigation and product clarity

Extract the shell currently embedded in `ChatWorkspace.tsx` into a workspace route layout. Keep workspace switcher and role visible everywhere; top-level destinations are **Ask**, **Knowledge bases**, **Compare versions**, **Your briefs**, then **Usage**, **Evaluation reports** and implemented administration tools. Group private conversation history separately from shared workspace knowledge. Preserve current user/workspace query keys, cache clearing, inert/focus behavior and role checks during extraction.

Replace vague entry copy with concrete ownership: “Ask questions across your organization’s knowledge bases. Sources are shared with workspace members; your conversations are private.” An empty workspace should show the editor’s next step, **Create a knowledge base**, while viewers see a useful explanation of who can add sources. A populated workspace should show selected source scope and **Browse knowledge bases**, not an upload-in-chat implication. Suggested prompts may be generic task starters, but must not imply knowledge of content that has not been retrieved.

## Functionality gaps to resolve before calling the UI complete

These are not cosmetic fixes. `ChatWorkspace` obtains its run only from `?run=` and renders `BriefControls` only for that active run’s message. History links omit `run`, while the current `Message` contract contains no run ID. Saving an older answer/recovering its proposal therefore needs an authorized message→run/execution discovery contract; do not patch it using localStorage or guessed IDs. Verify active-run resumption after ordinary history navigation for the same reason.

The route inventory has no members, settings or health page despite the frontend specification and existing backend endpoints. Conversation deletion also has no current UI control/API wrapper. Implement these product surfaces separately with role-aware controls, destructive confirmations, version-conflict handling and safe health information before final capability claims. Comparison context persistence likewise needs a contract review if existing read APIs cannot provide the selected sides. A CSS pass cannot satisfy these items.

## Implementation order and acceptance

1. Extract the shared shell and navigation without changing authorization/cache/stream behavior. Fix contrast, text size, input guidance and mobile document layout.
2. Refine the answer/evidence reading flow and knowledge/version screens, then comparison and brief review. Resolve the run/context discovery gaps with explicit API contracts and regression tests.
3. Add the missing specified administration/lifecycle UI; unify usage/evaluation styling and state components.
4. Review actual populated, empty, loading, permission-denied, failed, reconnecting, abstained and revoked-source states at360/768/1280/1440px,200% zoom, keyboard-only and reduced motion. Verify source focus restoration, mobile sheet scrolling, composer visibility with the keyboard, long filenames/titles, multiple citations, large revisions/history and role differences. Repeat axe after rendered states settle; add a screen-reader pass.
5. Only after full-pipeline proof and this visual acceptance, capture the authored synthetic organization walkthrough and final screenshots/videos specified in final-delivery. Keep diagnostic or fixture media labelled and separate.
