# Retrieval algorithm and authorization

## Selected profiles

`dense` V0 uses BGE cosine; `hybrid` V1 combines BGE and FastEmbed BM25 sparse vectors in Qdrant; `hybrid_rerank` V2 adds MiniLM (default candidate); `hybrid_rewrite` V3 rewrites once then V2. `sparse_bm25` is the offline sparse-only comparator. All variants use identical authorized corpus snapshots and generation settings. Qdrant is not permission authority. Read [index protocol](../05-database-and-storage/qdrant-index.md) and [collection config](../../contracts/config/qdrant.yaml).

1. Verify membership, allowed KBs, query limits and mode. Resolve active, nondeleted document revision IDs plus concrete index generation/collection in a short consistent PostgreSQL read. Compare instead resolves exactly two explicit authorized published/superseded revisions with live parents. No arbitrary historical retrieval in ask mode.
2. Cap eligible revisions at4096 for this capstone request; above that return422 with a scope-narrowing suggestion, never truncate or remove filters. Bind workspace_id, kb_id allowlist, revision_id allowlist and profile_id in **each** dense/sparse Query API branch. Read-only Qdrant key is server-only. Payload indexes exist before ingestion; strict mode rejects unindexed filtering.
3. Query named `dense` and `bm25` vectors, at most40 candidates each, one batch transport request where supported. Dense distance Cosine, query normalized finite384 floats. Sparse indices/values come from the pinned FastEmbed BM25 encoder; collection sparse modifier is IDF. Request IDs/scores/minimal payload only, no raw document text. Same source visibility filters in both branches.
4. Hydrate candidates from PostgreSQL with tenant RLS, explicit ownership/KB/revision checks, source hashes and current tombstones. Reject mismatched point metadata. Qdrant point payload is never prompt evidence. Drop stale/unauthorized candidates before fusion; never widen search to fill K. If active pointers changed, recompute once within deadline or use surviving authorized snapshot evidence marked stale-generation; new tombstones always veto use.
5. Fuse deduplicated authorized lists in application code using `sum(1/(60+rank))`, ranks start1, ties UUID ascending, union≤80. This fixes the RRF constant independently of server defaults and preserves branch rank diagnosis. Qdrant Query API prefetch/fusion is available, but not necessary for this controlled comparator.
6. Rerank top20; select≤8, pack≤3072 evidence tokens, dedupe identical source text. Comparison splits branch limits20 per side (40 per branch overall), fuses each side, takes up to10 rerank candidates per side and guarantees≥1 passage per side in final context; otherwise abstain. Recheck membership/source/privacy before provider egress and finalization.

Qdrant `exact=true` dense queries provide the same-filter reference for ANN Recall@20. Tune HNSW only against that reference under tenant skew1%/10%/80%, tombstones, staging and superseded revisions. Never relax filters for recall. BM25 IDF statistics are collection-wide; a tenant filter does not recompute tenant-only statistics. Freeze collection contents for paired experiments and report this relevance coupling. Scores/statistics are not public API fields; strict statistical tenant isolation requires separate collection policy and a new capacity review.

## Adaptive retrieval and no-result handling

No candidates: return completed abstention with suggestion to add/check sources, zero generation spend. Single branch failure: return marked degraded branch, never broaden scope. Both fail: `retrieval_unavailable`, not a false “no evidence” answer. Low evidence confidence: no universal cosine threshold. Fit optional threshold on development labels and freeze in config; until calibrated, request conservative answerability judgment under grounded prompt and report uncertainty. Reranker score is a rank signal, not probability.

V3 rewrite triggers only pronoun follow-up with antecedent or zero sparse and poor dense evidence on a development-calibrated threshold. One rewrite, max 256 output tokens, no more than two queries total including original, ≤2s additional target. Output schema `{query:string}`; immutable scope never appears as model-controlled arguments. Merge each branch's original/rewritten candidates with rank dedupe before global fusion. If rewrite fails, use original. It shares run budget/privacy and total deadline. Multi-hop loops and recursive autonomous searching are out of core.

## Provenance and diagnosis

RetrievalResult records normalized query hash, profile/config generation, chunk/revision IDs, branch ranks/scores, candidate counts, timing and degradation. Raw query and passages stay in authorized DB records, not telemetry. Reviewer evidence inspector can show ranks in an advanced debug view; normal users see source/version/page. Test dense/hybrid under same corpus/query set with Recall@20, MRR and nDCG@10; paired confidence intervals determine improvement, not selected screenshots.

## T15 implementation boundary

`retrieval/service.py` owns authorization and a15s retrieval deadline. `db/retrieval_repository.py` resolves and rechecks source scope; `retrieval/index.py` uses a read-only client; `retrieval/fusion.py` implements RRF60. Each request first checks exact scoped point count and presence of both named vectors, so missing index contents are unavailable rather than a false empty corpus. Valid empty BM25 document vectors are covered by a real-service test. Query batches contain at most two ask or four comparison searches; a transport failure permits one individually scoped rescue per branch. If every selected branch fails for a comparison side, the operation fails explicitly. No filter broadening occurs.

Before vector transport and again before hydration, current membership, source pointers, index availability and configuration are rechecked. A changed scope is resolved once; repeated changes fail with a retryable source-changed result. Returned passage text and provenance come only from authorized PostgreSQL chunks. Incorrect metadata in one branch cannot borrow a valid passage from the other branch to influence fusion. Candidate limits are20 total, with10 per comparison side; reranking/packing follow T16.

Dense query encoding applies the retrieval instruction recommended in the [BGE publisher model card](https://huggingface.co/BAAI/bge-small-en-v1.5), without adding it to stored passages. The original query remains unchanged for sparse retrieval and later generation. Query body is capped at256 embedding tokens and512 generation tokens; the additional instruction must fit the dense model cap. One shared CPU embedding slot can degrade a hybrid request to sparse-only while busy; dense-only evaluation fails explicitly in that case. This tradeoff is observable and remains a workload-tuning consideration.

Exact dense search remains the default. See the [measured diagnostic and limitations](../10-testing/retrieval-report.md). No ANN quality promotion is inferred from a small synthetic corpus. These retrieval entry points are internal; generation and user-facing source responses must still perform their own live authorization before egress.
