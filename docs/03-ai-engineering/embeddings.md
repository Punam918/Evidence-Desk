# Embedding contracts and migrations

Default `bge_small_en_v15` uses `BAAI/bge-small-en-v1.5`, 384 dimensions, float32 L2-normalized, cosine distance. CPU sentence-transformers inference with safetensors and immutable model/tokenizer revisions resolved in T01. Query instruction follows the [publisher card](https://huggingface.co/BAAI/bge-small-en-v1.5); no document instruction. Combined instruction+query must fit 512 tokens; API queries additionally limited to 256 BGE tokens for core retrieval. Documents have 384-token hard cap. Long query gets 422 with a narrowing suggestion; do not silently erase terms.

Batch documents initially 32, queries 1–8; process concurrency 1 and bounded queue 32. OOM halves batch once, retries once then fails cleanly; does not change model/dimension. Embedding timeout 15s/batch; per-job deadline 10min. Verify vector count/order, length=384, finite values and norm within 1e-3 of 1. Zero vector is error. Cache key binds workspace, embedding model revision, tokenizer revision, instruction version and normalized text hash. Cache does not grant access to text.

Storage baseline Qdrant named `dense` vector size384/Cosine plus `bm25` sparse vector; PostgreSQL index manifests track revision/count/hash/collection. Benchmark approximate search against exact Qdrant queries. No mixing of dimensions or normalization. A workspace's active `embedding_profile` and document revisions must agree. Reject startup/config that points to incompatible index schema.

Alternatives: [BGE-M3](https://huggingface.co/BAAI/bge-m3) for multilingual retrieval; 1024-dimensional candidate uses a separate versioned Qdrant collection. Managed embedding APIs reduce CPU setup but require paid-processor permission and separate spend tracking. Paid candidate `text-embedding-3-small`: default1536 dimensions and8192 input limit in the [official guide](https://developers.openai.com/api/docs/guides/embeddings), listed$0.02/million input tokens on the [model page](https://developers.openai.com/api/docs/models/text-embedding-3-small) as of research. Choose1536 rather than shortened dimensions for initial comparison; normalize/verify output, batch≤32 and≤16k input tokens/request as conservative project limits, retry429/503 with jitter max3. Separate1536-d collection and full reembedding required. Endpoint/model/account probe still required before enabling; not default. English-only v1 intentionally abstains on unsupported language instead of claiming multilingual retrieval quality.

Migration protocol: create new profile with pinned artifact/dimension/tokenizer; build side-by-side Qdrant collection and document revisions; backfill idempotently from originals/blocks; validate counts and paired recall; pause new publication briefly or dual-build queued revisions; atomically change workspace active generation once every live document is ready; invalidate retrieval caches; retain old generation 7d for rollback and old citation metadata as required. Never update vectors in place under old profile name. Rollback switches generation pointers; new documents built only in new generation require backfill before rollback. Deletion tombstones apply to both generations. Cross-dimension migrations need a new Qdrant collection configuration and verified manifests; PostgreSQL stores profile metadata, not a typed vector column.

Capacity estimate: 100k ×384×4 =153.6 MB raw vector values. Payload/sparse/index overhead and HNSW graph are additional and workload-dependent; benchmark actual collection sizes and RSS. This arithmetic is not a disk/RAM sizing guarantee.

## Sparse companion

FastEmbed `SparseTextEmbedding(model_name="Qdrant/bm25")` produces local document/query sparse vectors. Resolve and pin the model artifact and tokenizer configuration (English, lowercasing/stemming/stopwords, k=1.2, b=0.75, avg_len=256 if those are the verified pinned defaults); store their config hash alongside dense profile. Do not silently change parameters or reuse old sparse vectors. T01 verifies the actual pinned API/defaults and records any correction in qdrant.yaml before indexing. Use `query_embed` for queries and `embed` for documents. Unique sorted uint32 indices and finite values are required; empty sparse query means dense-only marked degradation. Qdrant supplies IDF; do not apply it twice. This fixed average-length FastEmbed BM25 formulation and collection-wide IDF must be named in evaluation reports rather than claimed identical to another engine's corpus-adaptive BM25.
